# Control4 ⇄ Modern Forms fan driver

Custom Control4 DriverWorks driver for Modern Forms (WAC Lighting) smart ceiling fans with integrated lights, over the fan's local HTTP API. Personal project for one home, public on GitHub under the Apache License 2.0 since 2026-10-27 (see "Licensing" below). Its process is copied from the owner's Hue project (corytron/c4-hue-driver), which is the reference for anything this file does not settle.

**The goal:** replace the stock `wac_mf_fan_and_light_controller(v4).c4z`, whose 13 Button Link connections do nothing in either direction (tested on the house 2026-10-27), with a driver whose fan speed links and light links really work with keypads and their LEDs, and whose state follows changes made in the Modern Forms app, the remote and the wall control. Then the house's keypad LED programming and its 1-second settle Timer agent are removed.

- **Plan first, then build.** For any new feature or fix, explore, then state the approach and the files you'll touch. **Standing approval (2026-10-27, carried over from the Hue project): I approve everything, every time** — plans, installs, Director restarts, Composer changes, deletes, merges. - **Edge cases before automation.** Before designing anything that acts on its own over the life of the system (finding a fan, following its IP, syncing names or rooms, creating or removing devices, migrating from the stock driver), send research agents to enumerate the lifecycle corner cases on both sides (Modern Forms and Control4: things added, moved, renamed, replaced, removed, reset, restored from backup) and decide per case what is automatic, what is only offered, and what is forbidden without a click. ## Working with agents

**Parallel by default.** For every piece of work, split it into parts that touch disjoint files and run them as background agents at the same time: module and its spec, VM-side tooling, changes to existing modules and their specs, docs and design notes. A single serial pass is only acceptable when the work truly cannot be split (one file, a handful of edits). Before starting any task, say in one line how it is being split and which agent owns which files; if it is not being split, say why.

- **Coordinator first.** Before spawning, write the contract the pieces share (an interface, a wire protocol, a file layout) into `docs/` so every agent builds against the same text. Then spawn them in one go, in the background.
- **One writer per file.** Each brief names the exact files the agent may create or edit and says that others are editing the rest of the checkout concurrently. No agent runs `git`; the coordinator integrates, runs `tools/check.sh` (every check CI runs) and `tools/build.sh`, and commits.
- **Briefs are self-contained.** Agents start cold: include the doc paths to read, the conventions (Lua 5.1, tabs, `.luacheckrc`, busted style, the fake C4 runtime in `tests/helpers/fake_c4.lua`), the hardware facts that matter, and what "done" looks like, including the verification commands to run.
- **Research agents are read-only** and write one new file under `docs/` (for example `docs/*-research.md` or `docs/edge-cases-*.md`), citing the SDK doc file for every API claim and the primary source for every Modern Forms claim.
- Typical split for a feature: VM-side tooling (Python) / driver-side Lua module plus its spec / changes to existing modules plus their specs / a design or research document. Integration into `driver.lua`, `driver.xml`, `tools/build.sh` and `CLAUDE.md` stays with the coordinator.
- Don't spawn for quick things (one file, a handful of edits); do it inline. Everything larger is split.
- Spawn every agent at the highest effort (`effort: "max"`; the owner calls it "ultracode"), whatever the task.
- While agents run, the coordinator does the integration pieces nobody else owns (`driver.lua`, `driver.xml`, `tools/build.sh`, `CLAUDE.md`) and verifies through the dev loop, rather than waiting idle.

## Targets

- **Control4:** must work on OS 3.x and OS 4.x controllers, managed from Composer Pro 3.x-era builds and the newer date-versioned Composer Pro releases. The house runs OS 3.4.3. Stick to documented APIs. The minimum OS is **3.3.0** (owner, 2026-10-27, #6: the `light_v2` brightness target; the driver's own Button Links need nothing newer), declared in `driver.xml` and checked at run time; the fan proxy's own per-speed connections (`proxy_fan_speed_connections`, OS 3.4.2) are not used in v1 (`docs/v1-design.md`).
- **Lua:** the controller's Lua sandbox (Lua 5.1 semantics, LuaJIT). No Lua 5.2+ features, no C modules, no `require` of anything not packaged in the driver.
- **Modern Forms:** the fan's local HTTP API (JSON POSTs to `http://<fan>/mf`, as `aiomodernforms` and Home Assistant use it; `docs/modernforms-api-research.md` says what is verified). Control4 must keep working when the vendor cloud is down.

## Scope (v1: the owner's decisions of 2026-10-27 in #6; the specification is `docs/v1-design.md`, the cutover `docs/migration-design.md`)

- Add a fan by the address the owner types; the driver pins its identity (client id / MAC), and a different fan at that address is refused until a click accepts it. No subnet scan; no Find Fans in v1. Gen 1–3 fans with six speeds only (Gen 4 is refused with a clear Status).
- **Fan:** the fan proxy with six discrete speeds, on/off (ON and Toggle at the proxy's preset speed, default 3), direction; the driver's own Button Links for Speed 1–6, Off, Toggle and Cycle, each handling DO_PUSH/DO_CLICK/DO_RELEASE and sending MATCH_LED_STATE so that a keypad's "Follow Connection" lights only the active speed (the pressed target at once, corrected if the fan disagrees). Double taps stay as keypad programming on the button's own events.
- **Light:** the light_v2 proxy with on/off, dimming (Default On Brightness) and Top/Bottom/Toggle Button Links with keypad LEDs, the way the Hue Light driver does them.
- **Live state:** the fan pushes nothing, so the driver polls (15 s idle, 2 s for 20 s after a change), one request in flight, the command's own answer authoritative; changes from the Modern Forms app, the remote and the wall control show up in Control4 promptly, never as late or out-of-order reports.
- Programming events (speed changed, light changed, fan offline) and useful Composer properties showing status; graceful handling of the fan offline (a wall switch that cuts its power), an IP change and a firmware change.
- The migration from the stock driver (`docs/migration-design.md`): cut over in one sitting with the stock programming disabled, not deleted; remove the stock device and the LED workaround in a later sitting once the driver's Migration Report shows nothing references it. `<replaces>` is forbidden.

Later, not v1: several fans managed together, the fan's sleep timer and schedules as Control4 features, other WAC product lines.

## Commands

- Checks: `tools/setup-checks.sh` once (installs the lint tools into `~/.local/bin`, no sudo), then `tools/check.sh` before every commit: the same checks CI runs as its four required jobs (`--strict` in CI; `--only <name>...` for a subset). Lint alone: `luacheck src tests tools`; tests alone: `busted tests`; Python tests: `python3 -B -m unittest discover -s tools/tests`; links alone: `python3 tools/check_links.py`.
- Build: `tools/build.sh` → `build/modernforms_fan.c4z` (one per `src/*/driver.xml`; `<version>` = git commit count) and `build/manifest.json`. `tools/build.sh --dev` adds the dev loop and the Lua command window; never install a dev build as the production driver.
- Dev loop (only while a `--dev` build is installed): `tools/devserver.py` (background, once, port 8081), `tools/devctl.py status|run|set|reload|wait|log|pin|unpin`; details in `docs/dev-loop.md`. While agents edit `src/`, keep the loop **pinned** and re-pin only states that pass lint and tests. Every bundle and command list is signed with the VM's dev key (`~/.config/c4-modernforms-driver/devkey`, created on first use): never print it, commit it or put it in a report, and never hand a `--dev` package to anyone, because it carries the key.
- **Current state: `docs/status.md`** (what runs on the house, what is built, what is open; update it when that changes). Index of the docs: `docs/README.md`. Design notes: `docs/design.md`; Composer checklist: `docs/composer-checklist.md`; feature contracts: `docs/*-design.md`; research: `docs/*-research.md`, `docs/edge-cases-*.md`; Composer automation: `docs/composer-remote.md`, `tools/composer/Composer.psm1`.
- Deploy (GitOps; the contract is `docs/cicd-gitops-design.md`): the house runs a GitHub release, never a VM build. Cut the release from the Actions page (Release ▸ Run workflow ▸ version) or push the tag; the workflow lints, tests, builds from `main` only and attaches the `.c4z` packages, `SHA256SUMS.txt`, `manifest.json` and the provenance attestations. Then a PR sets `deploy/house.yaml` (the desired state; `release: none` until the first install) to that build; on merge the drift workflow opens one issue labelled `deploy`. `python3 tools/deploy.py start` downloads and verifies the assets, creates the GitHub Deployment on the environment `house` (the observed state) and writes `build/release/<tag>/BRIEF.md`; send that brief to the Windows session: it fetches the files from the GitHub release URLs into `C:\c4-mf\drivers\<tag>\`, checks the hashes, installs them through Driver ▸ "Add or Update Driver or Agent…" (updates every existing device in place; never delete and re-add) and reads back every device's `Driver Version` and `Debug Mode`. `python3 tools/deploy.py done --devices N` records success and closes the issue; `failed --note` records what went wrong. A `<capabilities>` change still needs the owner to reboot the controller from System Manager (`start --note` carries that into the brief). `deploy.py status` says whether desired and observed agree. An install that bypassed the tool (a `--dev` build for the dev loop or a feature-branch hardware test, served from `build/release/` with `python3 -I -m http.server 8091 --bind 0.0.0.0 --directory build/release` and briefed with the hashes) is recorded afterwards with `deploy.py record --no-manifest` (before the first release, while `deploy/house.yaml` says `release: none`, with `--commit SHA` and no tag; drift is then reported but no issue is opened, since there is no release to install), so the drift issue shows the house is off its desired state until a release is installed again; a release install ends the dev loop. Stop the HTTP server afterwards.
