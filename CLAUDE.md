# Control4 ⇄ Modern Forms fan driver

Custom Control4 DriverWorks driver for Modern Forms (WAC Lighting) smart ceiling fans with integrated lights, over the fan's local HTTP API. Personal project for one home, public on GitHub under the Apache License 2.0 since 2026-10-27 (see "Licensing" below). Its process is copied from the owner's Hue project (corytron/c4-hue-driver), which is the reference for anything this file does not settle.

**The goal:** replace the stock `wac_mf_fan_and_light_controller(v4).c4z`, whose 12 Button Link connections do nothing in either direction (tested on the house 2026-10-27), with a driver whose fan speed links and light links really work with keypads and their LEDs, and whose state follows changes made in the Modern Forms app, the remote and the wall control. Then the house's keypad LED programming and its 1-second settle Timer agent are removed.

## Scope (v1: the owner's decisions of 2026-10-27 in #6; the specification is `docs/v1-design.md`, the house's cutover `docs/migration-design.md`)

- Add a fan by the address the owner types; the driver pins its identity (client id / MAC), and a different fan at that address is refused until a click accepts it. No subnet scan. **Found Fans fills by itself** (#102, `docs/auto-discovery-design.md`, since 1.2): one mDNS query for `_easylink._tcp.local` (3 s of answers; hardware check K10 passed, 2026-10-27) at every load and, while the device has no fan or no usable address, again after 30 s, 1, 2, 5 and 10 min, then every 15 min; a device whose fan answers asks only at load, one with a pin and an empty Fan Address never. A pick takes that fan at once, except a different fan on a pinned device, which waits for Use Selected Fan; the driver never adds a fan by itself, and the Find Fans action is gone. Gen 1–3 fans with six speeds only (Gen 4 is refused with a clear Status).
- **Names** (#37, `docs/fan-name-design.md`): the fan's product name from an exact lookup of its `fanType` in `fan/names.lua`, shown in Fan Model; the driver renames its own two items only on Use Selected Fan (and only while they carry the default names or the names it gave them) and on the action Name Items After Fan, never on its own.
- **Address follow** (#39, `docs/address-follow-design.md`): once a fan is pinned, when it stops answering at Fan Address (or something else answers there), the driver asks by multicast DNS for the pinned MAC on a backing-off schedule, reads an announced private address once, and moves only when that read shows the same client id and MAC (Fan Address and Last Action L30 say so). Never a subnet scan, never another fan; an address the owner typed wins until the fan answers there; `Follow Address Changes` (default On) switches it off.
- **Fan:** the fan proxy with six discrete speeds, on/off (ON and Toggle at the proxy's preset speed, default 3), direction; the driver's own Button Links for Speed 1–6, Off, Toggle and Cycle, each handling DO_PUSH/DO_CLICK/DO_RELEASE and sending MATCH_LED_STATE so that a keypad's "Follow Connection" lights only the active speed (the pressed target at once, corrected if the fan disagrees). Double taps stay as keypad programming on the button's own events.
- **Breeze** (#111, #121, `docs/breeze-design.md`, since 1.2; section 11 since 1.3): commands Breeze On/Off, Toggle Breeze and Set Breeze Strength (1–3) for programming, the `Breeze` variable, events Breeze Started/Stopped, the condition "Breeze is on", and keypad link 311 Fan Breeze. **Fan mode and Breeze mode exclude each other** (the owner's finding on their fan, 2026-11-07): the main fan device shows fan mode only (off while Breeze blows), a fan speed ends Breeze, an off stops the motor. The Navigators get a second fan device, the **Breeze fan** `modernforms_breeze_fan.c4z` (three speeds, Breeze 1–3; a new package since 1.3 because an installed device cannot change its proxy type; 1.2's light-type `modernforms_breeze.c4z` is no longer shipped), added only by the fan's action Add Breeze Fan and bound to the fan on binding 400 (class `MODERNFORMS_BREEZE`; messages `MF_BREEZE_STATE` / `MF_BREEZE_SET` / `MF_BREEZE_TOGGLE` / `MF_BREEZE_CYCLE` / `MF_BREEZE_HELLO` over `C4:SendToDevice`). "Breeze blows" means `wind` and `fanOn` are both true.
- **Breeze on the keypad LEDs** (#137, `docs/breeze-leds-design.md`, owner 2026-11-08/09): with `Breeze LED Animation` = Gusts (default Off) and `Speed LED Colors` = Per speed, the driver animates the bound speed links (301–306) while Breeze blows: dark first, then gusts running the way the fan blows (a white head with an ice, teal and sky-blue tail; rest by Breeze strength), and a wipe out once when Breeze ends, from any source; since 1.9 (#207) both animations pause while the keypad bound to Ambient Light Level (Follower) reads dark. Off, Toggle, Cycle, 311 and the light's links never animate. Colours and lit state only, never brightness, so the keypad's ambient dimming applies. `fan/breezeleds.lua` holds the animation; `links.lua` paints, settles and skips held pixels.
- **Light:** the light_v2 proxy with on/off, dimming (Default On Brightness) and Top/Bottom/Toggle Button Links with keypad LEDs, the way the Hue Light driver does them.
- **Live state:** the fan pushes nothing, so the driver polls (15 s idle, 2 s for 20 s after a change), one request in flight, the command's own answer authoritative; changes from the Modern Forms app, the remote and the wall control show up in Control4 promptly, never as late or out-of-order reports.
- Programming events (speed changed, light changed, fan offline) and useful Composer properties showing status; graceful handling of the fan offline (a wall switch that cuts its power), an IP change and a firmware change.
- Replacing the stock driver is a manual step the manual describes (the house's cutover is recorded in `docs/migration-design.md`); the driver has no migration report or stock-device row since #45. `<replaces>` is forbidden.

Later, not v1: several fans managed together, the fan's sleep timer and schedules as Control4 features, other WAC product lines.

## Commands

- Checks: `tools/setup-checks.sh` once (installs the lint tools into `~/.local/bin`, no sudo), then `tools/check.sh` before every commit: the same checks CI runs as its four required jobs (`--strict` in CI; `--only <name>...` for a subset). Lint alone: `luacheck src tests tools`; tests alone: `busted tests`; Python tests: `python3 -B -m unittest discover -s tools/tests`; links alone: `python3 tools/check_links.py`.
- **Parallel tooling** (owner, 2026-11-10, #183): the VM's cores and memory are used by everything that runs on it, and every new tool or toolchain is designed parallel from the start, with the same verdict and output as a serial run, in a fixed order. `tools/check.sh` runs its checks at the same time and prints each report in the usual order; inside, `LUA_INIT=@tools/luacheck_jobs.lua luacheck -j N src tests tools` (luacheck's own `-j`, in processes, no LuaLanes), `tools/busted_parallel.py tests` (one busted process per spec file, busted's own output) and `python3 -B tools/unittest_parallel.py discover -s tools/tests` (one process per test class, unittest's own output); `tools/build.sh` builds the drivers at the same time, byte for byte the serial packages. All take their width from `JOBS` (default `nproc`); `JOBS=1` runs everything serially with the plain commands above. The floor is the slowest spec file (`fan_driver_spec.lua`, about 3 s).
- Build: `tools/build.sh` → `build/modernforms_fan.c4z` and `build/modernforms_breeze_fan.c4z` (one per `src/*/driver.xml`; `<version>` = git commit count) and `build/manifest.json`. `tools/build.sh --dev` adds the dev loop and the Lua command window; never install a dev build as the production driver.
- Dev loop (only while a `--dev` build is installed): `tools/devserver.py` (background, once, port 8081), `tools/devctl.py status|run|set|reload|wait|log|pin|unpin`; details in `docs/dev-loop.md`. While agents edit `src/`, keep the loop **pinned** and re-pin only states that pass lint and tests. Every bundle and command list is signed with the VM's dev key (`~/.config/c4-modernforms-driver/devkey`, created on first use): never print it, commit it or put it in a report, and never hand a `--dev` package to anyone, because it carries the key.
- Probes (M1, #17): `probes/build_probe.sh` → `build/probe/mf_probe.c4z`, a throwaway Composer package for checks K4–K10 and K14 (`probes/README.md`), never installed as the driver and deleted after M1; `tools/mf_probe.py read|check|fixture` for the fan itself (`docs/fan-probe.md`): reads are free, the write checks (K11–K15) run only after the owner has been told what the fan will do and for how long, and every check restores the state it found.
- **Current state: `docs/status.md`** (what runs on the house, what is built, what is open; update it when that changes). Index of the docs: `docs/README.md`. Design notes: `docs/design.md`; Composer checklist: `docs/composer-checklist.md`; feature contracts: `docs/*-design.md`; research: `docs/*-research.md`, `docs/edge-cases-*.md`; Composer automation: `docs/composer-remote.md`, `tools/composer/Composer.psm1`.
- Deploy (GitOps; the contract is `docs/cicd-gitops-design.md`): the house runs a GitHub release, never a VM build. Cut the release from the Actions page (Release ▸ Run workflow ▸ version) or push the tag; the workflow lints, tests, builds from `main` only and attaches the `.c4z` packages, `SHA256SUMS.txt`, `manifest.json` and the provenance attestations. Then a PR sets `deploy/house.yaml` (the desired state; `release: none` until the first install) to that build; on merge the drift workflow opens one issue labelled `deploy`. `python3 tools/deploy.py start` downloads and verifies the assets, creates the GitHub Deployment on the environment `house` (the observed state) and writes `build/release/<tag>/BRIEF.md`; send that brief to the Windows session: it fetches the files from the GitHub release URLs into `C:\c4-mf\drivers\<tag>\`, checks the hashes, installs them through Driver ▸ "Add or Update Driver or Agent…" (updates every existing device in place; never delete and re-add) and reads back every device's `Driver Version` and `Debug Mode`. `python3 tools/deploy.py done --devices N` records success and closes the issue; `failed --note` records what went wrong. A `<capabilities>` change still needs the owner to reboot the controller from System Manager (`start --note` carries that into the brief). `deploy.py status` says whether desired and observed agree. An install that bypassed the tool (a `--dev` build for the dev loop or a feature-branch hardware test, served from `build/release/` with `python3 -I -m http.server 8091 --bind 0.0.0.0 --directory build/release` and briefed with the hashes) is recorded afterwards with `deploy.py record --no-manifest` (before the first release, while `deploy/house.yaml` says `release: none`, with `--commit SHA` and no tag; drift is then reported but no issue is opened, since there is no release to install), so the drift issue shows the house is off its desired state until a release is installed again; a release install ends the dev loop. Stop the HTTP server afterwards.
